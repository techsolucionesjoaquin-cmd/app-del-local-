# API REST implementada

Base `/api/v1`. La sesión se autentica por cookie y las mutaciones requieren `X-CSRF-Token`. Salvo `/auth/csrf`, login y demo (solo desarrollo), se exige usuario activo y autorización del servidor. Las rutas de módulo aplican restricciones de rol; un técnico accede a sus órdenes y proyectos. Usar `Idempotency-Key` única por comando (`K` abajo), con la misma clave/cuerpo al reintentar un fallo de red.

La respuesta JSON tiene `data`, `message`, `errors` y `meta`. En el listado de órdenes `data` incluye `items`, `page`, `pages` y `total`. Respuestas de adjuntos/firma y CSV son binarias/de texto con control de acceso. Los importes de mutación son cadenas decimales a la escala de la instalación; el frontend no decide el total. `401` sin sesión, `403` permiso/CSRF, `404` recurso fuera de alcance/no encontrado, `409` conflicto de inventario, caja, estado o replay distinto, `412` versión obsoleta, `422` campos inválidos y `429` límite de login.

| Módulo | Rutas principales y campos |
|---|---|
| Identidad | `GET /auth/csrf`; `POST /auth/login` con `login,password`; `GET /auth/me`; `POST /auth/logout`. `POST /auth/demo` solo en desarrollo habilitado. |
| Clientes/equipos | `GET/POST /customers`, `GET/PATCH /customers/{id}`, `GET /devices?customer_id=…`, `POST /devices`, `PATCH /devices/{id}`. Alta con `name`, documento opcional (`document_type`, `document`), contacto; equipo con `customer_id,type,brand,model,serial,os,notes`. Coincidencia de contactos pide revisión; RUT se valida con módulo 11. |
| Órdenes | `GET /service-orders?q=…&state=…&priority=…&technician_id=…&from=…&to=…&page=…`; `GET /service-orders/export`; `POST /service-orders` K; `GET/PATCH /service-orders/{id}`. El borrador admite campos parciales; `PATCH` controla `version`. `POST /service-orders/{id}/confirm` K: `version`, tres conformidades booleanas, firma opcional, `advance` si corresponde y `temporary_access` opcional. Confirmar devuelve número y estado. |
| Trabajo técnico | `POST /service-orders/{id}/transitions` K con `state,reason`; `POST /…/tasks`, `PATCH /…/tasks/{id}`, `POST /…/notes`, `POST /…/photos` multipart `file`. Lecturas de recepción `/receipt`, `/signature` y `/photos/{id}/content` protegidas. Revelación temporal por `POST /…/temporary-access/reveal` con contraseña y motivo. |
| Inventario | `GET/POST /products` (K al crear), `GET/PATCH /products/{id}`, `GET /catalog`, `GET /catalog/admin` y `POST/PATCH /catalog/admin/{categories,suppliers,locations,service_catalog}` según recurso. `PUT /products/{id}/technical-specs` y `/bios-support` (administrador). `GET /products/export`; `POST /products/imports/preview` y `/commit` K al confirmar, `{csv}`. No modificar existencias en altas ni CSV. |
| Reservas/compra | `GET/POST /stock-movements` K al registrar `product_id,kind,quantity,reason`; `POST /stock-reservations` K con `target,target_id,product_id,quantity`; `POST /stock-reservations/{id}/{release,consume}` K con `quantity,reason`. `GET/POST /purchase-requests` K al crear; `PATCH /purchase-requests/{id}` para administrar estado. |
| Armados | `GET/POST /pc-projects` K al crear; `GET /pc-projects/{id}` con componentes/evaluación/historial, `POST /…/items` K, `PATCH/DELETE /…/items/{item_id}`, `PATCH /…/firmware`, `POST /…/updates`, `POST /…/{transitions,duplicate,archive}` K. Cuerpo según operación: cantidades, prueba con `kind,note`, BIOS con `board_revision,bios_version`. |
| Presupuestos | `GET/POST /quotes` K al crear; `GET /quotes/{id}`; `POST /quotes/{id}/send` K con referencia de canal manual; `POST /quotes/{id}/approvals` K con `decision,channel,reference`. Crear recibe `target,target_id,valid_until,items`; armado aporta ítems del proyecto. Descuento solo por permiso autorizado. |
| Venta/pagos | `POST /sales/preview` con `items` y descuento opcional. `POST /sales` K agrega `fingerprint,session_id,customer_id,payments[]`. Cada línea uno de `product_id` o `service_id`, más `quantity`. Pago con `method,amount`, `tendered` para efectivo y `reference` para débito/transferencia. `GET /sales` y `GET /sales/{id}`; `POST /sales/{id}/void` K. `POST /payments` K con `receivable_id,session_id,payments[]`; `POST /payments/{id}/refunds` K. |
| Caja | `GET /cash-sessions/current`, `GET /cash-sessions/{id}`; `POST /cash-sessions` K con `register_id,opening`; `POST /cash-sessions/{id}/movements` K con `direction,amount,reason`; `/counts` y `/close` K con `counted,notes`. Una intervención ajena de administrador requiere `override_reason` donde el comando lo admite. |
| Operación | `GET /dashboard?days=7` o `14`; `GET /appointments?day=AAAA-MM-DD`; `POST /appointments` K con `day,time,kind,title,customer_id,order_id`; `PATCH /appointments/{id}` para estado. `GET /audit-logs`, `GET/POST /users`, `PATCH /users/{id}` solo administración. |

**Efectos críticos:** la reserva no baja físico; consumo/venta registran una salida en la misma transacción que la actualización de stock. La venta valida la huella de precios, usa solo stock disponible, e imputa medios al turno abierto. El anticipo no genera otra venta. La anulación genera entradas y devoluciones compensatorias y no altera un cierre anterior. Débito y transferencia no aumentan el efectivo esperado.
